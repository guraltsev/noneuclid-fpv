Finding (2026-11-04, batch 48-55). Bisect: the rename commit eccd27c is neutral; 35befce (motionState deleted, isTied added) causes it; 869024b recovered `flow` but not `flow+dependents` (~+1.5 us, 5%).

Evidence (deterministic): counting registry.getObjectsOfKind calls for the identical bench workload: job 50 (ee65c50) arcs = 201,972 calls; job 51 (869024b) arcs = 403,152. Caller attribution: all 201,180 extra calls come from `isTied <- resolveDerivedSegmentConnectionState` (segments.ts ~L302), called on every arc rebuild (each flow vertex move). Every other caller count is identical between the two commits. Job 50 read the stored field `motionState` there (O(1)).

Why it is costly: `getObjectsOfKind` is `[...set].map().filter()` (runtimeObjectRegistry.ts ~L348), O(objects of kind) and 3 allocations per call. So the job's claim that isTied is 'allocation-free' is false: the scan itself allocates.

Timings are too noisy to see this (flow+dependents varies +-2 us run to run, same as the effect, and rises when the machine is hot); use call counts.

Fix ideas, not applied: (1) give the registry an allocation-free iteration (forEachOfKind / reuse the per-kind id set) and use it in isTied, isVertexSharedWithOtherArc, arcsAtVertex; (2) do not recompute tied-ness per arc rebuild: derive the display state once per flow tick or keep a per-version index of arc ends per vertex; (3) pass the known tied state into the rebuild.

Tool used: temporary counter patched into getObjectsOfKind (not committed). Commits are still in git history (eccd27c..869024b) on branch batch-48-55.
