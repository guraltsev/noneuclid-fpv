Frame order in `createThreeApp.ts` on batch-48-55: `engine.step` (derive pass inside), then `advanceCurveShorteningPairs` and the refresh block, later `engine.endFrame()`, which calls `registry.changes.clear()` and `ticks.resetCursors()`. A write after the step is therefore wiped before any tick reads it. 013 6.3 says such writes stay until the next frame's readers saw them, which holds only for writes after endFrame.

Fix in design 014: absolute sequence numbers; endFrame moves the frame start and keeps tick cursors. `tests/engine/worldEngine.test.ts` has a test named "starts every cursor again after endFrame clears the journal" that pins the old behaviour and must change with it.

Related traps found in the same review: `guardRegistry` returns `{...registry}`, a different object from the registry but with the same `changes`, so anything keyed by registry identity (a WeakMap) splits in two with `module-write-guard` on; key by `changes` instead. `ModuleInstance` has no `reset` or `transformGeometry` although 013 9.1 lists them. The engine has no `transformGeometry`; the geometry commit is in the shell (`geometryCommit.ts`).
