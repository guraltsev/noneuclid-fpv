Checked in the code at ed5eed5 on 2026-11-05.

- A throwing command handler is stored as `world/internalError`, then `step` rethrows. `worldClient.afterStep()` is in the same `runPhase` closure after `engine.step` (createThreeApp.ts:1300-1301), so it is skipped and `endFrame` clears the results: the client never sees the result, a pending tool request stays stuck, `api.world.submit` never resolves.
- `startGeodesicCannonCarry` calls `prepareGeodesicCannonForLift` (deletes plain geodesics) and `enter-tool-mode` before `carry/attach` is answered, so a refused pickup has already changed the world and the tool.
- `enter-tool-mode` (rotate, aim, carry) bypasses `world/requestTool`, so tool gates never run for them.
- `runtimeObjectInstanceSyncRequested` is unread (`void` at createThreeApp.ts:1347): every `syncRuntimeObjectPortalInstances` dep is a no-op; the instance sync runs each frame anyway.
- `legacyWorldWriters` measures imports from files containing mutators, not writes. Per a read-only audit (not rechecked file by file): 8 of 14 listed files write nothing, while `toolObjectRuntimes.ts` and `runtime/worldGeometryComputedObjects.ts` write and are unlisted. Do not use its length as a debt metric.
- Measurement kinds are declared `transient` although 014 s2.1 calls their `geodesicId` and sides real; fix before any save format.
