# AGENTS.md assembler (`agents-md` drop-in)

## Design

**Status:** Implemented in `.agents/agents-md/`  
**Version:** 0.3

## 1. Purpose

`AGENTS.md` is read by Codex directly and by Claude Code through the `@AGENTS.md` import in `CLAUDE.md`. Its content
comes from several concerns (project summary, reading list, rules, commands, tool protocols such as the knowledge system
of [project-knowledge-system-design.md](../../_docs/project-knowledge-system-design.md) §7.7). Kept in one hand-edited file, those
concerns drift and collide.

The assembler keeps each concern in its own fragment and generates `AGENTS.md` and `CLAUDE.md` from the fragments.
Anything someone (a person or an agent) wrote directly into either file is not lost: it is detected and moved into a
fragment of its own before the files are regenerated.

The assembler is a hygiene script that a person runs by hand, like a formatter. It is not a skill, not an agent tool,
and not run by hooks. It is a drop-in ([coding_style.md](../../_docs/coding_style.md)): a self-contained folder copied into a
repository's `.agents/` and installed there.

## 2. Layout

```text
project-root/
  AGENTS.md                      generated, gitignored; at the root because Codex looks for it there
  CLAUDE.md                      generated, gitignored; at the root because Claude Code looks for it there
  _scripts/                      generated by install.py, gitignored; launchers that only call the script
    agents-md.cmd                for Windows shells
    agents-md                    for POSIX shells
  .agents/
    agents-md/                   the drop-in, tracked in Git
      agents-md.py               the script
      install.py                 installs the drop-in into the repository containing it
      agents.md.d/               template fragments copied to .agents/agents.md.d/ on first install
    agents.md.d/                 the source of truth, tracked in Git
      10-project.md              fragments: YAML frontmatter + Markdown body
      ...
      custom.md                  lines found in AGENTS.md that came from no fragment
      custom-claude.md           lines found in CLAUDE.md that came from no fragment
    .state/agents-md/            what the last build wrote, gitignored (§5)
```

A fresh clone has neither generated file until someone runs `install.py` and `build`, so agents working in a fresh clone
see no project instructions until then.

## 3. Installation

Copy the `agents-md` folder into `<repository>/.agents/` and run `python .agents/agents-md/install.py`. It:

- refuses to run unless its folder sits directly inside a `.agents/` folder;
- creates `.agents/agents.md.d/` if it is missing, by copying the template fragments from `agents-md/agents.md.d/`; an
  existing directory is left untouched;
- writes two launchers in `_scripts/` that only call `.agents/agents-md/agents-md.py` with their arguments; they find
  the script relative to their own location, so the repository can move;
- adds `/AGENTS.md`, `/CLAUDE.md`, `/_scripts/` and `/.agents/.state/` to `.gitignore` if missing.

Running it again changes nothing. It does not run a build.

## 4. Fragment format

```markdown
---
order: 20
description: Which project documents to read, and when.
---

## Read before working

...
```

| Field | Required | Meaning |
| --- | --- | --- |
| `order` | yes | Integer sort key. Ties are broken by file name. |
| `description` | yes | One sentence saying what the fragment is for. Not copied into the output. |
| `target` | no, default `all` | `all`: the fragment goes into `AGENTS.md`, which both runtimes read. `claude`: it goes into `CLAUDE.md` only. |
| `enabled` | no, default `true` | `false` leaves the fragment out of the output. |

There is no Codex-only target: Claude Code imports `AGENTS.md`, so anything in it reaches both runtimes.

The frontmatter is a restricted YAML subset: one `key: value` per line, where a value is an integer, `true`, `false`, or
a string (optionally quoted); blank lines and `#` comment lines are skipped. This lets the script parse it with the
standard library alone. Unknown or repeated fields and unknown `target` values are errors, so a misspelling is not
silently ignored. Every invalid fragment is reported at once, and nothing is written.

`custom.md` (target `all`) and `custom-claude.md` (target `claude`) have the same format with `order: 1000`, so custom
content comes last unless someone moves it.

## 5. Generation

`build`:

1. Reads and validates every `*.md` in `.agents/agents.md.d/`.
2. Detects custom lines in the current `AGENTS.md` and `CLAUDE.md` (§6) and appends them to `custom.md` or
   `custom-claude.md`, creating the file if needed. Custom fragments are written before the outputs, so a failure part
   way never loses hand-written lines.
3. Writes `AGENTS.md`: a one-line generated-file notice, then the bodies of the enabled `all` fragments in order,
   separated by one blank line.
4. Writes `CLAUDE.md`: the notice, the line `@AGENTS.md`, then the bodies of the enabled `claude` fragments in order.
5. Precedes each body with an HTML comment naming its source (`<!-- from .agents/agents.md.d/20-reading-list.md -->`),
   so a reader knows where to edit.
6. Writes a file only when its content changed, with LF line endings and UTF-8.
7. Saves what it wrote in `.agents/.state/agents-md/`, for the next comparison.

`check` does steps 1 and 2 without writing. It exits `1` when either file is missing, out of date, or contains custom
lines, and `0` otherwise. `--dry-run` on `build` prints the custom lines it would move and a diff of each output. An
invalid fragment makes every command exit `2`.

The repository root defaults to the one the drop-in is installed in (two levels above `.agents/agents-md/`); `--root`
overrides it.

## 6. Detecting custom lines

A line of a current output file is **custom** when, after removing trailing whitespace, it is not blank and is none of:

- a line the generator writes itself: a generated-file notice (of any wording, so older versions are recognised), a
  source comment, or (in `CLAUDE.md`) the `@AGENTS.md` line;
- a line of any fragment, enabled or not, of any target;
- a line of what the last build wrote to that file.

The last rule matters when a fragment changes: its old text, still in the output, came from the last build and is not
hand-written.

Custom lines are moved as blocks: consecutive custom lines, with the blank lines between them, stay together. Each block
is appended under a comment recording where it was found (the last Markdown heading above it, ignoring `#` lines in
fenced code):

```markdown
<!-- found 2026-11-01 in AGENTS.md after "Rules that are easy to miss" -->
- Never run the formatter on generated files.
```

Known limits, reported but not resolved automatically:

- **Edited lines:** a fragment line changed in place in an output becomes a custom line, and the original returns from
  the fragment on regeneration. The script reports such pairs ("possibly edited") so a person can move the edit into the
  fragment and delete the custom copy.
- **Deleted lines:** a fragment line removed from an output returns on regeneration. The script reports it as a warning;
  delete it from the fragment if the removal was meant.
- **Repeated lines:** a custom line identical to a fragment line, or to a line of the last build, is not detected.
- **No memory yet:** when there is no saved last build (a new clone, a deleted `.agents/.state/`, or outputs written by
  hand), and fragments were changed since the outputs were written, the old fragment text is taken for custom lines.
  The report shows them as possible edits; delete them from the custom fragment.

## 7. Interface

- `_scripts/agents-md build [--root PATH] [--dry-run]` (in Windows shells, `_scripts\agents-md build`)
- `_scripts/agents-md check [--root PATH]`
- Without the launchers: `python .agents/agents-md/agents-md.py build`.

Output is plain text for a person.

## 8. Non-goals

- Nested `AGENTS.md` files in subdirectories.
- Templating or variables inside fragments.
- Merging edits back into the fragment they came from. That is left to a person, helped by the report of §6.
- Running automatically (Git hooks, agent hooks, test runs) or being invoked by agents.

## 9. Open questions

- Whether fragments should be shareable across repositories (for example, a common rules fragment copied from this
